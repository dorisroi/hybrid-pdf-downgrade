\subsection{The consumer viewer: Adobe Acrobat}
\label{sec:acrobat}

pyHanko and DSS are command-line verifiers. The validator an end user actually
encounters is Adobe Acrobat, which additionally draws a graphical \emph{signature
panel}, so it is worth asking not only whether validation passes but what that
panel communicates. We opened every artifact in Adobe Acrobat Reader 26.002, the
free consumer build, with the test certificates left untrusted---the default
state a recipient sees---and signature checking on document open enabled.

For the decisive question---whether the downgraded document is distinguishable
from a legitimately classical-only one---the answer is not viewer-specific and
needs no run. A SHA-256 comparison confirms what Section~\ref{sec:attack} argues
structurally: the downgraded file is byte-identical to a document that was only
ever classical-signed, both in the plain case and at B-LTA. A deterministic
reader handed identical bytes produces an identical signature panel, so Adobe
Acrobat \emph{cannot} present the two differently; the same reasoning that made
the DSS report a consistency check (Section~\ref{sec:dss}) applies to the
graphical panel. The end user in the most common viewer has, by construction,
nothing to notice.

The panel then makes visible a finding the command-line tools only implied: the
downgrade makes the document look \emph{better}. Table~\ref{tab:acrobat} records
the banner Acrobat shows across the top of each file.

\begin{table}[htbp]
\caption{Adobe Acrobat Reader 26.002 signature banner, test certificates

\label{tab:acrobat}

\begin{tabular}{lll}
\toprule
\textbf{Document} & \textbf{Banner} & \textbf{Icon} \\
\midrule
Intact hybrid, order A          & \code{signature is invalid}      & red \\
Downgraded ($=$ classical-only) & \code{signature has problems}    & yellow \\
Intact hybrid, order B          & \code{signature is invalid}      & red \\

Intact hybrid, B-LTA            & \code{signature has problems}    & yellow \\
Downgraded B-LTA ($=$ cl.-only) & \code{signature has problems}    & yellow \\
\bottomrule
\end{tabular}
\end{center}
\end{table}

The intact order-A hybrid raises a red ``at least one signature is invalid,''
because this Acrobat build does not support ML-DSA and rejects the post-quantum
field outright---the same gap that makes DSS report that field as
\code{PDF-NOT-ETSI} (Section~\ref{sec:validatebetter}). The downgraded document,
from which that field has been truncated away, raises only a yellow ``at least
one signature has problems'': the surviving ECDSA signature is cryptographically
sound, and its sole defect is an untrusted self-signed identity, which would
clear once the signer's certificate is trusted. The attacked file therefore
presents \emph{less} alarmingly than the protected original---the ``validates
better'' inversion is not confined to a command-line report but is what a lay
user sees in the panel of the most common PDF reader. Every file still carrying an
ML-DSA field (order-A intact, order-B intact, and the order-B post-quantum
residue) is marked invalid for the same reason, a transition-period artifact that
will pass as readers add ML-DSA support. In the B-LTA set the intact and
downgraded files instead share the same yellow banner, so there the downgrade
does not look better; the red-to-yellow inversion is specific to the plain
order-A case the attack targets. Screenshots accompany the artifact bundle.
